# Responses Compat：最终优化方案

日期：2026-09-24（Asia/Shanghai）

状态：按用户要求完成的最终方案建议；方案 B 已选定。本文件不是代码、更名、部署或发布已经完成的声明，也不代替实施授权。

## 1. 最佳命名与产品定位

**推荐项目名：Responses Compat。仓库名、命令名：`responses-compat`。**

中文说明：Responses API 兼容性代理。

一句话定位：在不接管账号管理和模型路由的前提下，针对客户端、代理与上游之间已验证的 Responses API 实现差异，提供可配置的适配和显式降级。

选择依据：

- Responses 明确协议边界，不暗示支持所有模型 API。
- Compat 说明同一 API 不同实现之间的兼容问题，不预设客户端“不标准”或上游“有缺陷”。
- 去掉 Muse 和 Codex：二者是当前目标上游和客户端，不是长期产品边界。
- 相比 Responses Bridge，Compat 更不容易被理解成 Chat Completions、Claude、Responses 之间的协议转换桥。
- 相比 Responses Gateway，不暗示账号池、计费、负载均衡和管理平台。

因此，用 Responses Compat 替代此前的 Responses Bridge 命名建议。名称并未获注册或排他性保证；公开发布前需针对实际托管账号、分发渠道核查可用性，不能把搜索未命中当成商标或名称可用证明。

公开说明必须区分“具备可配置能力”和“已验证某个真实上游”。Muse 是首个目标配置；其他上游不因采用 `/responses` 路径就自动获得兼容认证。

## 2. 根因判断与证据原则

本项目不定位为“纠正 Codex 非标准请求”，也不统一宣称“补全上游 Responses”。

截至本日核实的官方资料和本地源码，只能支持以下分项结论：

| 差异 | 当前判断 | 规则性质 |
|---|---|---|
| 本地引用与递归 Schema | 官方公开能力包括递归；具体请求是否满足所有约束及失败层次仍需个案证据 | 引用展开是适配；回边改成 `{}` 是有损降级 |
| namespace、additional_tools | 已在官方文档公开；不能仅凭字段存在认定请求不标准 | 保留结构，按已验证对象遍历，不擅自扁平化 |
| 超长工具名称 | 当前代码以字节数 64 为阈值；已确认的公开 64 限制来自 Chat Completions，不能直接作为所有 Responses 名称字段的依据 | 可配置的命名适配，归因待验证 |
| reasoning ID 重放 | 官方有无状态 reasoning 重放机制；当前删除 ID 的根因尚无链路对照证明 | 路由特定的既有绕过策略，不是通用清洗 |
| SSE 首事件前刷新响应头 | 本仓库已有对应修复提交 | 代理自身正确性，不归责于协议两端 |

详细依据及不足见 `docs/compatibility/2026-09-24-evidence-register.md`。单元测试、源码注释和“改写后能工作”的历史陈述不能替代同一请求的链路证据。

## 3. 架构边界

```text
Codex / Responses 客户端
  → CLIProxyAPI（入口、账号选择、模型路由）
  → Responses Compat 实例（固定上游、显式兼容配置）
  → 指定 Responses 上游
```

首阶段单进程、单上游、单套兼容配置。不同上游可启动不同实例，仍由 CLIProxyAPI 路由。

包含：配置与启动校验、模型白名单、Schema/名称/reasoning 规则、JSON/SSE 有界处理、请求取消、脱敏诊断和契约测试。

不包含：凭据存储、OAuth、账号池、模型发现、模型名重写、负载均衡、跨上游容灾、自动生成重试、跨 API 协议转换、工具执行、动态插件、管理 UI、热更新、公网多租户服务。

仅保留 `GET /healthz`、`POST /v1/responses`。healthz 只表示本地服务可用，不检查或承诺上游、模型和凭据健康。

## 5. 配置契约

使用标准库 JSON，新入口为 `--config <path>`。不新增配置框架。

- 无参数启动保留原 Muse 行为，这是升级兼容默认值，不是适用于所有上游的通用默认值。
- 指定配置文件时必须显式指定 profile；不自动识别提供方，不因配置错误回退到 Muse。
- 配置只在启动时加载。未知键、重复键、尾随 JSON、非法值及未知版本均拒绝。
- `config_version=1`；必填 `listen`、`upstream_base_url`、非空 `models`、`profile`。
- models 为精确模型 ID 白名单，不自动发现、不使用通配符、不重写模型名。
- profile 为 muse 或 passthrough；预设解析后应用显式 transforms 覆盖。新上游从 passthrough 开始，只开启必要规则。
- 不允许凭据字段；授权仍由 CLIProxyAPI 随请求提供。
- 可选 `extra_request_headers`、`extra_response_headers` 为头名数组，默认空；只配置头名，不配置值。合法性校验、大小写无关去重及逐跳头排除在启动/请求阶段执行。

```json
{
  "config_version": 1,
  "listen": "127.0.0.1:18317",
  "upstream_base_url": "https://opencode.ai/zen/go/v1",
  "models": ["muse-spark-1.3-contributor"],
  "profile": "muse"
}
```

| 配置项 | 取值 | muse | passthrough |
|---|---|---|---|
| transforms.schema_refs | preserve / inline | inline | preserve |
| transforms.recursive_refs | reject / empty_schema | empty_schema | reject（仅 inline 时生效） |
| transforms.tool_name_max_bytes | null 或 16–256 整数 | 64 | null |
| transforms.reasoning_ids | preserve / drop | drop | preserve |

null 禁用名称适配；阈值按 UTF-8 字节数计，不声称等于任何上游的字符限制。muse 中保留 drop 和 empty_schema 是为避免升级改变既有行为，不意味着其根因已证实。

上游必须为启动配置中的固定 HTTPS 地址，禁止 userinfo、query、fragment；仅字面量回环 IP 可使用 HTTP 测试。监听只允许字面量回环地址与合法端口。URL 不能来自客户端请求，不跟随上游重定向。

## 6. 变换契约与重点优化

请求流程：有界读取 → JSON 对象/模型校验 → 根据配置建立请求级工具映射 → 名称、Schema、reasoning 变换 → 固定上游转发。

### 6.1 默认保留

passthrough 对通过校验的正文保留原始字节，不因检查模型而重编码。没有实际变换的其他配置也尽可能原样转发。未知字段不因兼容清洗而删除；HTTP 逐跳头和传输编码不在逐字节透传承诺内。

### 6.2 Schema

inline 仅处理本地引用，不联网解析外部引用。不支持、无法解析的引用明确失败；不得在不知情时删除约束。preserve 不主动解析或拒绝这些引用。

empty_schema 明确放宽递归位置的约束；reject 在需要展开却遇到递归时拒绝。保留现有请求 32 MiB、展开预算和 Schema 深度 64 的边界，不在第一阶段增加动态资源调优配置。

### 6.3 工具名称

继续覆盖 tools、嵌套 namespace 工具、additional_tools、tool_choice、输入 function_call。保留 namespace 结构，不自动把 namespace 与 name 拼接。

名称超限时采用确定性哈希别名；碰撞拒绝。默认 64 字节配置下必须与旧算法一致。其他长度策略的输出满足上限，不把可逆映射写入磁盘，不跨请求共享可变映射。改变长度配置应在会话边界执行。

优化重点：从“任意 name 字段递归替换”收窄为已识别工具对象和有契约测试的事件路径。普通对象的 name、用户文本和 arguments 字符串不能被误改。JSON 与 SSE 必须使用同一请求映射和恢复规则。

### 6.4 Reasoning 与服务端状态

只有 drop 删除输入 reasoning 项的 id；encrypted_content、summary 和其他字段保留。禁止删除整个 reasoning 项或尝试解析加密内容。

撤销旧草案中“名称适配 + previous_response_id 一律 422”的规定：当前没有足够证据支持把这种拒绝作为普遍修复。

首阶段不新增 previous_response_id 专属拦截，保持已有请求处理；但不承诺请求级映射能恢复仅存于上游会话中的历史名称。完整工具声明的无状态重放是首阶段可测试、可承诺的模式；仅依赖服务端历史的模式明确列为未验证，不自动切换为无状态、不暗中跨请求缓存，也不把“透传了该字段”称为完整支持。

如果真实用例表明必须恢复缺失的历史映射，该场景不得标为已支持；需另行评审状态管理设计，或者经批准增加精确适用的拒绝规则。请求级已知映射的失败关闭保证不能扩展到不可知的历史别名。

### 6.5 JSON/SSE 与 HTTP

- 非 2xx 保留状态和正文，不执行成功响应的名称恢复。
- 无名称映射时流式转发。有映射时对支持的 JSON/SSE 有界改写，成功保留上游状态。
- JSON 输入及改写后输出限 64 MiB；SSE 原始帧及改写后完整帧限 64 MiB，包含 event/data 封装开销。
- JSON 读取或改写失败，在提交响应头前返回 502。SSE 已开始后，适配失败发送终止 response.failed 并停止，不再输出成功终止符。
- 需要恢复名称却遇到不支持的成功媒体类型时，明确 502，不静默绕过恢复。
- 不自动重试、换账号、换上游或在流中间重启生成。传播取消，保留现有超时和优雅退出。
- 覆盖 LF/CRLF、多行 data、注释、EOF 尾帧、逐步刷新及慢客户端测试。
- 拒绝复制 Host、Content-Length、Content-Type、Accept-Encoding 等受控请求头以及逐跳头；响应不能沿用改写前的长度/编码。排除 Connection 额外声明的头，且不能被配置白名单重新放行。

以上名称恢复范围、完整帧预算和媒体类型处理是待实施的正确性优化，不是对当前版本已具备能力的描述。每项先构造回归样例，再改变实现。

## 7. 最小内部组织

采用静态 Go 组合：配置解析层、HTTP 转发层、请求适配层、响应适配层。规则使用小型类型化策略，不引入动态插件或通用任务编排器。

保留 schema.go、tool_names.go、response_rewriter.go 的可复用算法；让 server.go/main.go 消费解析后的实例配置，不在业务路径按 provider 名称散布分支。具体接口和拆分在实施计划中确定，避免设计阶段无根据地生成大量接口。

## 8. 证据、诊断和隐私

每条规则记录：ID、问题样例、出现边界、公开契约、原始结果、单项改写结果、适用版本/路由、语义损失、退出条件和核实日期。文档证据、源码行为、模拟测试与真实链路验证分开标记。

最小归因观察点：A 为 Codex 发给 CLIProxyAPI；B 为 CLIProxyAPI 发给 Adapter；C 为 Adapter 发给上游及上游响应。比较 A/B 判断中间转换，比较 B/C 判断适配效果。同一路由/账号条件下每次仅切换一项规则。

不建设默认全量录包功能。真实请求只在独立授权后用最小合成内容复现；不读取已有私人提示词、会话或凭据。存入仓库的只能是合成或人工去敏并复核过的结构样例，不保留授权、加密 reasoning、真实工具参数或完整会话标识。

运行日志仅含本地请求 ID、profile、规则 ID、计数、耗时、状态和固定错误类别。配置校验不回显原文件、完整 URL 或秘密。必要诊断与面向用户错误都不得泄漏正文。
